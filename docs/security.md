# Security Model

- Access tokens are short-lived JWTs.
- Refresh tokens are random, stored only as SHA-256 digests, rotatable and revocable.
- Passwords use PBKDF2-SHA256 with a configurable work factor and must be at least 12 characters.
- Sessions are kept in the client's session storage only: closing the desktop app or ending the browser session signs the user out, and every launch starts at the sign-in page.
- Self-service accounts (`REGISTRATION_MODE`): `approval` (default) creates them as PENDING with no access until an administrator approves them and assigns a role; `open` activates them as INVESTIGATOR (only cases they create or are assigned to); `disabled` turns sign-up off. Account status is only disclosed after a correct password, so sign-in errors do not reveal which emails exist.
- Backend permissions are enforced independently of UI visibility.
- CORS is explicitly configured.
- Uploaded evidence filenames are reduced to safe basenames.
- Upload size is bounded by configuration.
- Original evidence is chmod'd read-only after hashing.
- Audit records form a hash-linked chain with verification endpoint.
- Report downloads require `REPORT_READ` and access to the case.
- WebSockets require a valid access token, and live events (case, evidence, job, finding and report changes) are only delivered to members of the case concerned and to administrators.
- Offline changes synced from a workstation (`/desktop/sync/push`) go through the same case-access and permission checks as the online API; only whitelisted fields are written, workstation custody events are labelled `DESKTOP_*`, and offline audit events are appended to the hash chain under one fixed action name.
- The audit log shows administrators every record; other roles with `AUDIT_READ` see their own actions and actions on cases they can open.
- Evidence hashes are always computed by the server; a SHA-512 sent with an upload is only used to confirm the transfer, and a mismatch discards the upload.
- Internal `.local` email domains are accepted for accounts (common for on-premises directories).
- An image is registered once per case: an upload whose SHA-256 is already registered in the case is refused and discarded.
- Deleting evidence needs `EVIDENCE_DELETE` (administrators and investigators) and a reason, is refused while an analysis of the image runs, and is recorded in the chain of custody and the audit log; the item's history is kept.
- A case under legal hold (`LEGAL_HOLD_MANAGE`, administrators and investigators; a reason is required to place and to release it) blocks evidence deletion for everyone, administrators included (HTTP 423). Case edits and offline sync cannot change the hold.
- Tags need `FINDING_CREATE` and case access; adding, changing and removing them is audited.
- Hash sets are imported and deleted only with `HASHSET_MANAGE` (administrators); both are audited (`HASHSET_IMPORTED` with the source's SHA-256, `HASHSET_DELETED`). Server-side imports take a plain file name in `storage/hashsets/incoming` (no folders, no hidden files, no symbolic links). Every user can see which sets exist.
- Programs are analysed, never run: pefile and signify parse them in-process; capa, clamscan and freshclam run through `run_tool` (no shell, own process group, memory and time limits, cancellation) on a copy under a generated name. Only administrators (`RULES_MANAGE`) add or remove YARA rule sets and ClamAV databases; a rule set is compiled before it is accepted and may not `include` files (which could read files on the server), a database must load in clamscan, and every change is audited (`YARA_RULESET_*`, `CLAMAV_DATABASE_*`, `CLAMAV_UPDATE_STARTED`).
- VirusTotal lookups are off for every case until an investigator with `CASE_UPDATE` turns them on for that case (audited); then only the SHA-256 of programs is sent, never a file, a name or a path, at the configured rate. The API key is read from the environment and never stored in jobs, records or logs.
- Uploads: file names are reduced to a plain name (no folders), each upload is written to a new folder of its own, and an image set is checked (complete, in sequence, parents present) before anything is registered; a refused set is discarded. Every file of a set is hashed and re-hashed by integrity checks.
- Logical packages are unpacked without trusting them: a name with `..` is refused and absolute names stay inside the package, links and special files are never created, archive bombs are refused before anything is written, every file is hashed and left read-only, and the manifest's hash goes into the chain of custody. Collected files are only read, as on a disk.
- Linux and macOS files are parsed as data: XML (recently-used.xbel) with defusedxml, plists with plistlib, SQLite databases read-only from copies; `/etc/shadow` is read only for whether a password is set and when it changed: hashes are never stored.
- Phone extractions are parsed as data: SQLite databases read-only from copies, XML with defusedxml, Android binary XML by DFIP's own bounds-checked reader, plists with plistlib. Wi-Fi passwords are skipped as the files are read and never stored or returned. Encrypted app stores and backups are not decrypted.
- Network captures are only parsed: tshark and capinfos run through `run_tool` (no shell, own process group, limits, timeout, cancellation); nothing is replayed, rendered or contacted. Files carried in a capture are stored under their SHA-256 and served like other members (sniffed, `nosniff`, sandboxed; audited). Hosts and addresses from a capture go to threat-intelligence providers only when an investigator presses Look up (`ANALYSIS_RUN`, audited).
- Imported Plaso timelines are read as text (JSON lines and CSV), never evaluated; the file is kept read-only with its SHA-256, imports and deletions are audited, and importing needs `ANALYSIS_RUN` and case access.
- Keys of encrypted volumes are checked against the volume before they are kept, then stored only encrypted (Fernet: AES-128-CBC with HMAC-SHA256, key derived with HKDF-SHA256 from `DATA_ENCRYPTION_KEY`, or `JWT_SECRET` when it is not set). They are never returned by the API, written to job payloads, results, logs or the audit trail (validation errors do not echo them); the decryption job receives only the key's reference. Unlocking, failed attempts, each use and deletion of a key are audited. The decrypted volume is new, read-only evidence with its own hashes and custody records; the encrypted original is unchanged.
- Shadow copies, virtual disks and encrypted volumes are read with libyal libraries in-process, read-only; working copies and decrypted copies are made only after a free-space check.
- Content search: every search is audited with its query; user regular expressions run in RE2 (linear time, bounded memory) under a 15-second limit. Text extraction never runs document code: Office and OpenDocument XML is parsed with defusedxml with size limits, PDFs go through `pdftotext` and SQLite databases through a separate read-only process, both under `run_tool` limits.
- Archives and embedded files are opened without trusting their member names: members are written under generated names, only regular files inside a fresh folder are taken from 7-Zip (links never followed), external tools run with a file-size limit, and size, expansion-ratio and total limits stop archive bombs. Encrypted members are listed, never decrypted. Unallocated space is streamed from `blkls` and never written to disk; reading raw volume bytes is audited.
- NTFS volumes are read by libfsntfs from the evidence's read-only image; alternate data streams are read for hashing and a text preview only (a stream's content is shown as text or hex, never run); journal paths come from the MFT, never from the evidence's own claims.
- Email HTML is never rendered as received: the browser sanitises it with DOMPurify (no scripts, forms, event handlers, frames, `<base>` or `<meta>`; links disabled, only `data:` pictures kept) and shows it in an `<iframe sandbox>` (no scripts, opaque origin) whose own Content Security Policy is `default-src 'none'; img-src data:; style-src 'unsafe-inline'`, so nothing is fetched from the internet (tracking pixels included). Inline pictures come from the stored attachments as `data:` URIs. Opening a message is audited (`EMAIL_VIEWED`). Attachments are stored under their SHA-256, never under their own names, and viewed like other files.
- Saved browser passwords (and Firefox's encrypted user names) are never decrypted, copied into the database or returned by the API: only that a password is saved. Chat apps with encrypted stores are listed, never decrypted. Every browser, chat and cloud database is opened read-only on a copy; deleted SQLite rows are carved from the copied bytes, never by writing to a database.
- Pictures and videos are decoded under limits: Pillow refuses pictures over 64 million pixels; ExifTool, ffprobe, ffmpeg, pdftoppm and tesseract run through `run_tool` (no shell, own process group, memory limit, timeout, cancellation). Generated thumbnails and keyframes are stored under SHA-256 names and served with `nosniff`, `attachment` and a sandbox CSP; each one served is audited. The map is bundled; the app never contacts a map server, and OpenStreetMap is opened only when the user follows its link.
- Thumbnails are stored under their SHA-256 (never a name from the evidence), sniffed from their bytes, served only as images with `nosniff`, `attachment` and a sandbox CSP, and every view is audited (`FILE_CONTENT_VIEWED`). SQLite databases (ActivitiesCache.db, Windows.db) are opened read-only on copies; ESE databases are read by libesedb, never by Windows' own engine.
- Event logs are parsed, never executed or rendered: libevtx renders each record's XML and defusedxml parses it (entities refused); the event's XML is shown as text. Detection rules are YAML loaded with `safe_load`, validated when they load (unsupported modifiers, conditions or log sources are refused), and their regular expressions run in RE2. Event log search escapes the user's text before matching.
- Card and Aadhaar numbers found in evidence are shown masked in lists, search results and reports; showing one in full needs case access and is audited (`SENSITIVE_VALUE_REVEALED`, without the value).
- File processing reads evidence files in-process and never executes them or opens them with their own application: types come from libmagic, Office containers are parsed with olefile, ZIPs only have their central directory read, and YARA scans the bytes with a timeout per file. Encrypted files are flagged, never decrypted.
- Findings are reviewed by someone else: approving or sending back needs `FINDING_REVIEW` (administrators and investigators) and is refused to the author; only the author (or an administrator) edits, reopens or deletes a finding, an approved finding is locked until reopened, and every step is kept in its history and the audit log. Findings cannot be deleted under legal hold.
- Comments: an @mention notifies only people who can already see the case; mentions of anyone else are reported back to the writer and never notified, so a mention cannot reveal a case. Edits keep the earlier text; deleting leaves a marker; all are audited.
- Physical evidence: custody actions must fit the item's state, a check-in records the seal's state (a broken seal notifies the case's investigator), release and destruction are refused under legal hold, and photos are accepted only as JPEG or PNG by their content, stored under their SHA-256 and served with `nosniff` and a sandbox CSP.
- Case summary and Claude mode: the summary is built inside DFIP from stored records. Claude mode is off for every case until someone who may update the case turns it on; then only the summary facts the investigator ticks, and the question, are sent to the Anthropic API (no files, no other records), through the official SDK with the key from `ANTHROPIC_API_KEY` (never stored, logged or returned). Every request is kept with exactly what was sent and its SHA-256, and audited; answers must cite the facts, and citations of facts that were not sent are flagged.
- Retention: closing a case starts its retention period; a daily check only notifies administrators. Deleting a case needs `CASE_DELETE` (administrators), the case number typed to confirm and a reason; it is refused under legal hold, while work runs and while physical evidence is still held. The case remains as a deleted record with its chain of custody and audit trail.
- Signed reports: every report PDF is signed (PAdES) with the organisation's certificate (`REPORT_SIGNING_P12`, its password in `REPORT_SIGNING_P12_PASSWORD`) or, without one, a self-signed certificate DFIP makes once and keeps as an encrypted PKCS#12 (passphrase derived with HKDF-SHA256 from `DATA_ENCRYPTION_KEY`, or `JWT_SECRET`); checks report it as self-signed and not trusted. With `REPORT_TSA_URL` an RFC 3161 timestamp shows when it was signed (PAdES-B-T); if the authority cannot be reached the report is signed without it and the reason kept. Checking a report shows whether anything was changed or added after signing, who signed, and whether the certificate and the timestamp chain to the configured roots (`REPORT_TRUST_ROOTS`, `REPORT_TSA_TRUST_ROOTS`); nothing is fetched while checking. A report that cannot be signed is kept unsigned and says why.
- HTML reports are one self-contained file: no scripts, nothing fetched (its own policy `default-src 'none'; img-src data:; style-src 'unsafe-inline'`), pictures inline as `data:` URIs, every text escaped (only bold, italic and line breaks are kept from the report's markup, and a stray `<` never opens a tag); served as an attachment with `nosniff` and a sandbox CSP.
- Exports need `REPORT_EXPORT` (administrators and investigators). A table export reads the view with the user's own credentials, so it holds only what the user can see there, and only table views of this API can be named. Spreadsheet formulas are defused (CSV injection: text starting with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading apostrophe; XLSX cells are written as text). CASE/UCO, STIX and MISP exports hold hashes, names, paths and hosts, never file contents, with the TLP marking the investigator chooses. Every export is audited with its SHA-256.
- Pictures of findings are accepted only as PNG or JPEG by their content (up to 10 MB), stored read-only under their SHA-256, served with `nosniff` and a sandbox CSP, and added or removed only by the author while the finding can be edited.
- File content shown in the viewer is read without writing a copy, typed from its first bytes (never from the name), never rendered as HTML, and served with `nosniff`, `attachment` and a sandbox CSP; each view is audited as `FILE_CONTENT_VIEWED`.

For production, add TLS, encrypted storage, secrets management, network segmentation, MFA/SSO, rate limiting at the edge, malware sandboxing, SIEM integration, backups, retention controls and periodic security assessment.
