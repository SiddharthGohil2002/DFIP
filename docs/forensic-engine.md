# Forensic Engine

## Evidence safety model

The API stores an acquisition hash before analysis, marks the original object immutable, changes its local filesystem mode to read-only, and records custody/audit events. Analysis receives a path to the preserved object and never receives a write capability by design.

## Adapter boundary

`app/forensic/tools.py` contains an allow-list for specialist utilities. Commands are executed without a shell, with bounded time and output, and only through named tool adapters.

Supported integration points:

- The Sleuth Kit: `fls`, `istat`, `fsstat`, `mmls`
- ExifTool
- tshark
- YARA
- Volatility (`vol`)
- strings

Tool availability is exposed by `GET /api/forensics/tooling`.

## Full analysis pipeline

`POST /api/jobs/analysis/{evidence_id}` queues a `FORENSIC_ANALYSIS` Celery job (`app/tasks.py`) that runs `app/forensic/pipeline.py`. After the integrity check (step 1), the work is done by **analysis modules** (`app/forensic/modules/`), each owning its own output; see *Analysis modules and profiles* below. In order:

1. **Integrity**: re-hash the original image (SHA-256) and refuse to continue if it no longer matches the acquisition hash. The check is logged to the chain of custody.
   - **E01/EX01 only** (`app/forensic/working_image.py`): the Sleuth Kit build in the image (4.12 with libewf 20140816) crashes on EWF images, so the E01 is checked with `ewfverify`, exported once with `ewfexport` to a raw working copy in `storage/analysis/working/<EVID>.raw`, trimmed to the media size and compared with the MD5 stored in the E01. A corrupt E01 or a mismatch stops the analysis. The copy (read-only) is recorded in the chain of custody as `WORKING_COPY_CREATED` with its SHA-256, and every later tool (`mmls`, `fls`, `icat`, `istat`, carving) reads it. The uploaded E01 is never modified and is still what integrity checks hash.
2. **Partitions** (module `fs_index`): `mmls`; every non-meta, allocated, non-extended slot is examined. An image without a partition table is examined at offset 0.
3. **Filesystem index**: per partition, `fsstat` (filesystem type) and `fls -r -m /` written to a bodyfile under `storage/analysis/pipeline/<EVID>/<JOB>/`. Every entry, allocated or deleted, goes into the `fs_entries` collection (`app/forensic/filesystem.py`).
4. **Timeline**: one `FILE_MACB` event per distinct timestamp of each entry, labelled like `mactime` (`m.cb` etc.) (`app/forensic/timeline.py`). The bodyfile is kept so results can be re-checked with `mactime -b`.
5. **Artifact extraction** (module `artifacts`, `app/forensic/artifact_locator.py`): known paths are selected from the file index and copied out with `icat`, keeping their names and SQLite `-journal`/`-wal` sidecars:
   - Chrome / Edge / Brave / Chromium `.../User Data/<profile>/History`
   - Firefox `.../Profiles/<profile>/places.sqlite`
   - `Windows/System32/config/SYSTEM`
   - `Windows/INF/setupapi.dev*.log`
   - `$Recycle.Bin/<SID>/$I*` (paired with the matching `$R*` content), `Users/<user>/AppData/Roaming/Microsoft/{Windows,Office}/Recent/*.lnk`, `Windows/Prefetch/*.pf`
6. **Browser history** (`app/forensic/browser_artifacts.py`): visits and downloads (Chromium `urls`/`downloads`; Firefox `moz_places` and `moz_annos` download annotations), stored as `BROWSER_HISTORY` / `BROWSER_DOWNLOAD` artifacts and timeline events.
7. **USB history** (`app/forensic/usb.py`, using `regipy`): `Enum\USBSTOR` (vendor, product, revision, serial, friendly name), `Enum\USB` (VID/PID), `MountedDevices` (drive letter, volume GUID), and the device-property timestamps `0064` first install, `0065` last install, `0066` last arrival, `0067` last removal (Windows 7 and 8+ layouts). `setupapi.dev.log` first-install times are converted to UTC with the hive's `ActiveTimeBias`. Results go to `usb_artifacts` and `USB_ACTIVITY` timeline events.
8. **Windows activity** (`app/forensic/windows_activity.py`): Prefetch files (libscca, including Windows 10/11 compressed files) give the programs that ran, their run count, up to eight last-run times and the files they loaded; shortcuts in the Recent folders (liblnk) give the files the user opened, the drive they were on (type, serial, label) and the target's own times; Recycle Bin `$I` records (v1 and v2) give the original path, size and deletion time. Stored as `PROGRAM_RUN`, `RECENT_FILE` and `RECYCLE_BIN_ITEM` artifacts, with `PROGRAM_RUN`, `RECENT_FILE_OPENED` (the shortcut's own times: created = first opened, modified = last opened) and `FILE_DELETED_TO_RECYCLE_BIN` timeline events. At most 2,048 Prefetch and 5,000 shortcut and `$I` files are parsed per analysis.
9. **File hashes and types** (module `fileproc`): every file in the index, allocated or deleted, is read once in-process (pytsk3, 1 MiB chunks, in disk order) for MD5, SHA-1 and SHA-256, its type from the first 64 KiB (libmagic, never the name), entropy and encryption markers; see *File processing and hash sets* below.
10. **Archives and embedded files** (module `containers`, Full profile): members of archives, media and objects embedded in Office documents, PDF attachments, two levels deep, become file-index entries; see *Archives, embedded files and unallocated space* below.
11. **Hash sets** (module `hash_match`): every file's hashes are looked up in the imported hash sets; known-bad and notable files become `HASH_SET_MATCH` indicators.
12. **YARA** (module `yara`): programs, scripts, documents and archives anywhere on the disk, chosen by their real type from `fileproc` (bounded: 20,000 files, 32 MiB each, 8 GiB in all), are read in-process and scanned with yara-python and `backend/rules/default.yar` (60 s per file); matches become `MALWARE_INDICATOR` artifacts, deleted files included.
13. **File contents** (module `content`, Full profile): the text of every file that has any goes into a per-evidence SQLite FTS5 index; see *Content search and found data* below.
14. **Unallocated space** (module `unallocated`, Full profile): the strings of every file system's free blocks, with their volume offsets, in a second content index.
15. **Found data** (module `found_data`, Full profile): email, web and IP addresses, phone, card, IBAN, cryptocurrency and Aadhaar numbers recognised and validated in that text, stored in `entities`.
16. **Tags** (runs after every job): tags on this evidence's items are re-linked to the new records by their natural key (see `app/services/tags.py`).
17. **Case analytics** (runs after every job): patterns and anomalies are recomputed for the case.

Everything written carries `analysis_job_id`, `pipeline_module` and `module_run_id` for provenance.

- **Profiles:** `quick` (time zone, file system index, computer, artifacts, registry: no file hashing or YARA), `standard` (every module except the content ones, so also event logs, file hashes, hash sets and YARA; the default when the request has no body) and `full` (everything: also `containers`, `content`, `unallocated` and `found_data`). A request may instead name `modules`.
- **Run plan:** the requested modules, plus any prerequisite that has not completed (or was written by an older module version), plus every module that depends on something being re-run, or *follows* it (reads its output when it ran, without needing it), and had completed before. Re-running `yara` runs only `yara`; re-running `fs_index` also refreshes `artifacts`, `fileproc`, `hash_match` and `yara`; importing or deleting a hash set re-runs only `hash_match`.
- **Own output only:** a module first deletes its previous documents (`pipeline_module=<name>`), unsets the fields it adds to other modules' documents (`fileproc` and `hash_match` on `fs_entries`) and its facts; nothing else is touched, so the other modules' records keep their IDs. Output written before modules existed (no `pipeline_module`) is replaced as a whole by a standard run.
- **Status:** each module's status, version, run ID, counts and first warnings are kept on the evidence (`modules.<name>`); `analysis_summary` and the job summary merge the counts of every module's latest completed run, so a partial re-run still reports the whole evidence. All warnings go to `pipeline_warnings`; the job summary keeps the first 200 (`warnings_total` has the number).
- **Jobs:** one analysis per evidence at a time (another request returns 409). A worker claims a queued job atomically and sends heartbeats; a redelivered message for a job another worker owns, or that already finished, is ignored (`DUPLICATE_IGNORED`). If a worker dies, the job is taken over once its heartbeat is 10 minutes old and continues after the modules it had completed. The Celery visibility timeout is longer than the longest allowed analysis, so a long job is not redelivered while it runs.
- **External tools** run through `run_tool` (`app/forensic/modules/base.py`): no shell, an own process group, a 4 GiB address-space limit, a timeout, and a cancellation check every 2 seconds that kills the whole process group.
- **Work folders** (`storage/analysis/pipeline/<EVID>/<JOB>/`) of earlier jobs are removed once no module's current output refers to them.

### Time zone, computer and users

- **Time zone** (`tz_probe`, `app/forensic/timezone.py`): before the file system is indexed, the SYSTEM hive is read in-process (pytsk3) and `ControlSet\Control\TimeZoneInformation` gives the Windows zone (`TimeZoneKeyName`), the offsets and the daylight-saving rules. The zone is mapped to IANA with Unicode CLDR's `windowsZones.xml` (`app/forensic/windows_zones.py`, release 48-2; e.g. Eastern Standard Time -> America/New_York); a zone without a mapping is turned into an exact POSIX TZ string from the hive's own rules (`STD5DST4,M3.2.0/2:00:00,M11.1.0/2:00:00`). An investigator can set the zone on the evidence (`PUT /api/evidence/{id}/time-zone` with a reason, audited); that re-runs `tz_probe` and everything built on it. Without a SYSTEM hive the zone is UTC and FAT volumes are flagged.
- **Conversion:** `fls -z <zone>` lists FAT and exFAT (which store local time) in that zone, so `fs_entries` and `FILE_MACB` events hold true UTC; each FAT entry records the zone used (`time_zone`) and `atime_date_only` (FAT keeps only the date of the last access; access events carry `access_date_only`). `setupapi.dev.log` is converted with the same zone, daylight saving applied per date. Local times in the repeated hour when clocks go back are read as the first (daylight) occurrence. The backend image includes `tzdata` and `tzdata-legacy` for the zone names.
- **Computer** (`computer`, `app/forensic/system_info.py`): SYSTEM (computer name, last shutdown, network interfaces with an address), SOFTWARE (edition, display version, build and UBR, install date, registered owner, user profiles with their last load, last signed-in user) and SAM (machine SID; per user the V record's name, full name and comment, and the F record's last logon, password last set, logon and failed-logon counts and account flags). Accounts are joined with profiles by SID; profiles without a local account (domain or Azure AD users) are listed too. Each result lists the hives it came from with their SHA-256. Recycle Bin items show the user name for their SID.

### Registry activity

- **Hives** (module `registry`, every profile): each user's `NTUSER.DAT` and `UsrClass.dat`, `Amcache.hve`, `SYSTEM` and `SOFTWARE` are copied out of the image with their `.LOG1`/`.LOG2` transaction logs. A dirty hive (its primary and secondary sequence numbers differ) has the logs applied with regipy before it is read, and the hive list records whether that was needed. User hives are attributed to their owner through the SOFTWARE profile list (profile folder -> SID).
- **Per user:** UserAssist (programs started from Explorer: ROT13-decoded names with known-folder GUIDs resolved through the user's profile, run count, focus count and time, last run; Windows XP control values skipped), ShellBags (folders browsed, from `UsrClass.dat` and Windows XP `NTUSER.DAT`, with the shell item's created, modified and accessed times and NTFS reference; libfwsi/libfwps through regipy; "last browsed" is the key's write time for the most recently opened folder at each level), WordWheelQuery (Explorer searches), TypedPaths and TypedURLs, RecentDocs (own parser: MRUListEx order, per-extension lists), RunMRU (own parser: MRUList order), the user's Run and RunOnce keys, Terminal Server Client (remote desktop servers and user name hints) and mapped network drives (`Network`).
- **Computer:** Amcache `InventoryApplicationFile` (path, SHA-1 from `FileId`, size, version, publisher, link date; the key's write time is about when Windows first recorded the program), ShimCache (the current control set's AppCompatCache only, in order, with each file's modification time, without the `\??\` prefix), BAM (last run per user SID, the device path shown without `\Device\HarddiskVolumeN`), automatic services (boot, system and automatic start; image path and service DLL), SOFTWARE Run/RunOnce (and their 32-bit and policy variants), Winlogon `Shell`/`Userinit` and Image File Execution Options debuggers, and installed programs (Uninstall keys with a display name).
- **Flags** on autostart entries: a program in a user profile, ProgramData or a temporary folder; PowerShell with an encoded command, a hidden window or a bypassed execution policy; a script host or system binary often used to hide programs (mshta, rundll32, regsvr32, wscript, cscript); every IFEO debugger; a Winlogon value that differs from the Windows default.
- **Timeline:** program runs (UserAssist, BAM), programs recorded (Amcache), folders browsed, the latest Explorer search, typed path, Run dialog command and recent document of each list, autostart entries (services only when flagged), installed programs, remote desktop connections and mapped drives. The activity dashboard counts the user-activity ones.
- **Execution evidence** (`app/forensic/execution.py`, `GET /api/forensics/execution`): one row per program (by file name), with every Prefetch, UserAssist, BAM, Amcache and ShimCache trace, the paths it was seen at, the latest run and the earliest record. ShimCache alone is shown as "on the disk; no trace of running".

### Jump lists, Timeline, thumbnails, SRUM and the search index

- **Jump Lists** (module `user_activity`, standard and full profiles): every `*.automaticDestinations-ms` (OLE compound file: a shell link per item and the `DestList` stream, versions 1 to 4, with the last-used time, pin position, use count, computer name and distributed-link-tracking object identifiers, from which the MAC address of the computer that made the target's object ID is shown) and `*.customDestinations-ms` (the application's named categories, Frequent and Recent lists and Tasks; a damaged file is scanned for shell links) in each user's `Recent` folder. Applications are named from 16 well-known AppIDs; others show their AppID. Each AutomaticDestinations use becomes a `JUMPLIST_OPENED` timeline event.
- **Windows Timeline**: `ActivitiesCache.db` under `AppData/Local/ConnectedDevicesPlatform/<account>` (SQLite, opened read-only on a copy with its write-ahead log): activities opened (type 5), time in use (type 6, `activeDurationSeconds`), clipboard copies (type 10, the copied text decoded) and copy and paste (16), with the application from the AppId JSON (executable path, Win32 identifier or package; known-folder GUIDs resolved), the display text, description and content URI; and `ActivityOperation`, whose operation type 3 is an entry the user deleted from the Timeline before it was synchronised. Each becomes a `TIMELINE_ACTIVITY` timeline event.
- **Thumbnails**: each user's `thumbcache_*.db` (the CMMM layouts of Windows Vista, 7 and 8 to 11): every entry with a picture (JPEG, PNG or BMP, with its size from Windows 8 on) is stored by its SHA-256 and viewed like a recovered file. The entry hash is the thumbnail cache ID, which links a thumbnail to the file the Windows Search index knows by that ID.
- **SRUM**: `Windows/System32/sru/SRUDB.dat` (ESE, libesedb): network data usage, network connectivity and application resource usage, with applications and users resolved through `SruDbIdMapTable` (users named through the evidence's accounts and the well-known service SIDs; device paths shown without `\Device\HarddiskVolumeN`). The Network usage tab totals bytes sent and received per application and user.
- **Windows Search**: `Windows.edb` (ESE; `SystemIndex_0A` or `SystemIndex_PropertyStore`, column names with or without the property number) and Windows 11's `Windows.db` (SQLite property store): path, name, folder, size, created, modified, accessed, indexing time, owner, kind, a summary of the text and the thumbnail cache ID. Text columns are decompressed by libesedb; binary numbers and FILETIMEs are big-endian; the summary is de-obfuscated (an XOR mask from the value's size, as libesedb's esedbexport documents). Each entry on the C: drive is checked against the file index (on disk, deleted, or not on the disk); entries no longer on the disk become `SEARCH_INDEXED` timeline events.

### NTFS internals

- **Volumes** (module `ntfs`, standard and full profiles): every NTFS file system the file index found is opened with libfsntfs at its partition offset; every MFT entry from 24 on that has a `$FILE_NAME` is read (deleted entries included), with its path from libfsntfs's path hint (orphans under `$Orphan`). The file system's own files (`/$...`) are skipped.
- **Timestomping**: the `$STANDARD_INFORMATION` times are compared with the long name's `$FILE_NAME` times. **Strong**: the `$SI` creation time is more than a second earlier than the `$FN` creation time, the `$SI` created, modified and accessed times are one whole-second value, and the `$FN` time has a fraction (what SetFileTime-based tools leave; Windows then sets the change time to the moment of the change, which becomes the event's time). **Possible**: an earlier, whole-second `$SI` creation time in a user's folder (`\Users\<name>\`, `\Documents and Settings\<name>\`). An earlier, whole-second creation time elsewhere is normal (Windows and installers keep the installation media's times): a real Windows XP `$MFT` of 13,060 entries has thousands of those, and no strong or possible match.
- **Alternate data streams**: every named `$DATA` stream with its size, SHA-256 and (for text) its first 2,000 characters; streams Windows itself writes are named (Mark of the Web, SmartScreen, Thumbs.db marker, WOF compression, macOS metadata), others are left unnamed for review. `Zone.Identifier` is decoded (ZoneId with its name, HostUrl, ReferrerUrl) and becomes a `FILE_DOWNLOADED` timeline event at the file's creation time. Streams open in the file viewer through their file-index entry (`inode-128-id`).
- **USN change journal** (`$Extend/$UsnJrnl:$J`): every record (versions 2 and 3; version 4 range records are skipped) with its file and parent references, time, reasons, attributes and name, stored in `usn_records` (up to 1,000,000). Paths are resolved through the parent folder's MFT entry when its sequence number still matches. Each change's closing record (`CLOSE`, which holds all its reasons) becomes a `USN_CHANGE` timeline event when it creates, deletes, renames (with the old name), overwrites, changes times or attributes, or adds or removes a stream.

### Browser depth

- **Profiles** (module `browser_depth`, standard and full profiles): Chrome, Edge, Brave, Vivaldi and Chromium (`AppData/Local/<vendor>/User Data/<profile>/`), Opera and Opera GX (`AppData/Roaming/Opera Software/Opera Stable/`, with or without a profile folder) and Firefox (`AppData/Roaming/Mozilla/Firefox/Profiles/<profile>/`). Every database is copied out with its `-wal` and `-journal` and opened read-only on the copy; a missing table leaves that part out with a warning. The `artifacts` module reads Opera and Vivaldi history and downloads with the other Chromium browsers.
- **Searches**: Chromium's `keyword_search_terms` (with the time of the search's visit), and search addresses in the history of every browser (Google, Bing, DuckDuckGo, Yahoo, Yandex, Baidu, Ecosia, Startpage, YouTube, Wikipedia, Amazon).
- **Cookies** (Chromium `Cookies` or `Network/Cookies`, Firefox `cookies.sqlite`): host, name, path, created, expires, last used, flags. Chromium values are encrypted (DPAPI) and shown as such; Firefox keeps them in clear.
- **Bookmarks** (Chromium's JSON `Bookmarks`, Firefox `moz_bookmarks`) with their folders; **form history** (Chromium `Web Data` `autofill` and saved cards without their numbers, Firefox `formhistory.sqlite`); **saved logins** (Chromium `Login Data`: site, user name, when saved and last used, times used; Firefox `logins.json`: site and times, the user name is encrypted). Passwords are never decrypted, stored or shown.
- **Deleted history** (`sqlite_recover.py`): rows of `urls` and `keyword_search_terms` (Chromium) and `moz_places` (Firefox) still in the database file or its write-ahead log. Freelist pages are read through their cell pointers (row ID kept); free space in pages in use (freeblocks, whose first 4 bytes SQLite overwrites with its own fields, and the unallocated gap) is searched in two passes: whole cells first, then records whose header that overwrite cut, never overlapping a whole cell; every frame of the current `-wal` generation is read, and a row whose row ID is live with other values is an older version. A record is attributed to a table only when every column fits the table's declared types, its text decodes cleanly and, for history, its visit time is a real date. Chromium and Firefox build SQLite with secure delete, which zeroes deleted rows in the database file itself: in their files deleted rows survive mainly in write-ahead logs (Firefox) and in pages copied before the deletion.

### Email

- **Mailboxes** (module `email`, standard and full profiles): Outlook PST and OST files anywhere on the disk (libpff: every folder, including orphan items, which are marked deleted), MBOX files (`.mbox`, `.mbx`), Thunderbird folders (`Profiles/<p>/Mail|ImapMail/<account>/<folder>`, subfolders in `.sbd`; the `.msf` summaries are skipped) and single `.eml` and `.msg` files (up to 5,000; MSG read with olefile).
- **Messages** (`email_messages`): folder, sender, To/Cc/Bcc, sent time (the Date header or PR_CLIENT_SUBMIT_TIME) and received time (the newest Received header or PR_MESSAGE_DELIVERY_TIME), subject, the text and HTML bodies (256 KiB and 1 MiB kept), the transport headers, the originating IP, flags and whether it was sent or received (by its folder). Thunderbird keeps messages the user deleted in the folder file until it is compacted (`X-Mozilla-Status` 0x0008): they are listed and marked deleted.
- **Attachments and inline pictures** are saved under their SHA-256 and become file-index members (`<mailbox>!/<folder>/message <n>/<name>` for a PST, `<mailbox>!/message <n>/<name>` for a single folder): hashed and typed by the same code as other files, matched to hash sets, scanned by YARA and indexed for content search; re-running `email` re-runs those.
- **HTML** is never shown as sent: the API returns it with inline (`cid:`) pictures turned into `data:` URIs and a count of remote references; the browser sanitises it with DOMPurify (no scripts, forms, event handlers, frames or links) and shows it in an `<iframe sandbox>` whose own Content Security Policy allows only `data:` pictures and inline styles, so tracking pixels and remote styles are never fetched.

### Pictures and videos

- **Which files** (module `media`, standard and full profiles): every file whose content is a picture or a video (file processing's type, not the name), allocated or deleted (content as on the disk now), archive members and email attachments included; up to 50,000 pictures (200 MiB each) and 2,000 videos (2 GiB each).
- **Thumbnails**: Pillow, upright by the EXIF orientation, at most 320 pixels on the long side, JPEG, stored under the file's SHA-256 (the same content shares one). Pictures over 64 million pixels are refused (decompression bombs); a picture Pillow can't decode is marked unreadable with the reason.
- **Metadata**: ExifTool, in batches (camera make and model, lens, software, the original date, its offset, GPS position and time, serial numbers, comments, and the QuickTime tags of videos). **When a picture was taken**: DateTimeOriginal is local time; it is made UTC with the offset the picture records (OffsetTimeOriginal), else its GPS time stamp, else the computer's time zone, else it is shown as recorded; the basis is kept with the time. A position of exactly 0, 0 (no fix) is ignored.
- **Videos**: ffprobe (length, codecs, size, frame rate, the creation time, which QuickTime/MP4 stores in UTC, and an ISO 6709 location); keyframes with ffmpeg: the first frame and each scene change (scene score over 0.3), at most 6; when that gives fewer than 3, frames at even intervals.
- **Map**: locations are drawn on Natural Earth's 1:110m land outlines (public domain), bundled with the app (`scripts/build-world-map.py`); nothing is loaded from a map server. OpenStreetMap is offered as a link the user follows (on the desktop, an address to copy).
- **Text in pictures and scans** (module `ocr`, full profile): tesseract (English) reads every picture at least 200 x 60 pixels (converted to an upright greyscale PNG, at most 4,000 pixels across) and every PDF whose first 10 pages have no text (rendered at 200 dpi by pdftoppm), up to 2,000 files. The text is stored on the file's entry; the content index uses it (method `ocr`), so content search and found data cover it.

### Chat and cloud storage

- **Skype (classic)** `main.db` (module `chat_cloud`): accounts, contacts, every message (markup removed, emoticons keep their text, the kind of each non-text message), calls with their members and length, and file transfers with their direction, status, file name, path and size.
- **Detected, not parsed**: Microsoft Teams (classic and new), WhatsApp (Microsoft Store and older desktop), Telegram Desktop, Signal, Skype 8, Slack, Discord and Zoom keep messages in encrypted databases or browser caches. Their folders are listed per user with the number of files, size, deleted files, the newest change and why they are not read.
- **OneDrive** (`settings/<Personal|BusinessN>/SyncEngineDatabase.db`): every file and folder the client knew, with full paths, size, last change, disk times, shared flag and hash (`localHashDigest`: SHA-1 for personal accounts, QuickXorHash for business). A SHA-1 is looked up among the file hashes of the evidence, so a synced file is linked to the same content on the disk, in an archive or attached to an email. **Google Drive for desktop** (`DriveFS/<account>/metadata_sqlite_db`): items with paths, size, modified, viewed, shared-with-me and trashed. **Dropbox** (`info.json`): accounts and their local folder (its file list is encrypted).

### Windows event logs

- **Reading** (module `eventlogs`, standard and full profiles): every `.evtx` file under `Windows/System32/winevt/Logs` is copied out and read with libevtx (pyevtx), including records libevtx recovers from unused space in the chunks (flagged `recovered`). Each record's XML, as libevtx renders it with its template, is parsed with defusedxml: the System fields (event ID and qualifiers, provider, channel, TimeCreated to the microsecond, record number, computer, user SID, process and thread), the EventData values (named, `ComplexData` included, or the list of unnamed values of classic logs) and the UserData fields (flattened, with nested elements named by path). Control characters in values (not allowed in XML 1.0) are kept. A record whose XML cannot be parsed keeps libevtx's own fields and says why. Limits: 250,000 records per log, 1,000,000 per evidence item, 16,384 characters per value and 32,768 of XML per record. Windows XP `.evt` logs are reported, not read.
- **Meaning** (`app/forensic/event_catalog.py`): 96 catalogued events in 12 logs: Security, System, Application, PowerShell (classic and Operational), Task Scheduler, Terminal Services, Microsoft Defender, Partition/Diagnostic, Kernel-PnP and DriverFrameworks, identified by channel and event ID and by provider where providers share an ID (System 7001 is a Winlogon logon, or a service dependency failure from the Service Control Manager). Each has a category, a plain-English description built from the event's data (logon type names, failed-logon reasons from the NTSTATUS code, group members, who cleared a log), the user it is about (computer and service accounts left out; SIDs named through the evidence's accounts and through the events themselves, so a deleted account is still named) and whether it is notable. Logons by SYSTEM, LOCAL SERVICE, NETWORK SERVICE, computer accounts and service logons are kept but not notable; PowerShell 4104 script blocks are notable when Windows logged them as suspicious (level Warning). PowerShell `-EncodedCommand` (and every abbreviation PowerShell accepts) is decoded and shown with the event.
- **Detections** (`app/forensic/sigma_lite.py`, rules in `backend/rules/sigma/`): a subset of Sigma run on every record as it is read: log sources by service or category, search identifiers as maps, lists of maps and keyword lists, values with wildcards, the `contains`, `startswith`, `endswith`, `all`, `re` (RE2, with `i`, `m`, `s`), `cased` and `windash` modifiers, conditions with `and`, `or`, `not`, parentheses, `1 of`, `all of` and `them`, and `| count([field]) [by field] > n` over a sliding `timeframe`. A rule using anything else is refused when the rules load. The 15 curated rules cover cleared logs, services installed from user or temporary folders, encoded PowerShell, PowerShell download cradles, accounts created, deleted and added to Administrators, password guessing (more than 10 failures from one address in 10 minutes) and spraying, Defender detections and protection turned off, suspicious scheduled tasks, Remote Desktop logons and audit policy changes. Each detection keeps up to 200 matched records; matched records are notable.
- **Timeline and USB:** notable records become timeline events (`LOGON`, `LOGOFF`, `LOGON_FAILED`, `ACCOUNT_CHANGED`, `LOG_CLEARED`, `SERVICE_INSTALLED`, `SERVICE_CHANGED`, `SCHEDULED_TASK`, `POWERSHELL`, `SYSTEM_STARTUP`, `SYSTEM_SHUTDOWN`, `TIME_CHANGED`, `DEFENDER_ALERT`, `PROGRAM_INSTALLED`, `SHARE_ACCESS`, `AUDIT_POLICY_CHANGED`); the activity dashboard counts logons and logoffs. USB device events (Partition/Diagnostic 1006, Kernel-PnP 400/410/420, DriverFrameworks 2003/2100/2102, UserPnp 20001/20003) are matched to the USB devices by serial number (from the parent USB instance ID, a USBSTOR instance ID or the disk's serial): matched devices gain `eventlog_events` and first/last connected and last removed times, unmatched ones are added with source `EVENT_LOG`, and each connect and remove becomes a `USB_ACTIVITY` event.

### File processing and hash sets

- **One read per file** (`fileproc`, `app/forensic/filetypes.py`): files are sorted by inode (roughly their order on the disk) and read in 1 MiB chunks; the same pass feeds the three hashes, a byte histogram of the first 4 MiB (Shannon entropy) and the first 64 KiB for the type. A deleted file is hashed as its content is on the disk now (`hash_basis` says so; its clusters may have been reused). A file that can't be read gets `hash_error` and is counted as unreadable.
- **Type:** libmagic (python-magic, the `file` command's database) on the first 64 KiB. libmagic 5.46 can't recognise a ZIP from a buffer (its rules read the end of the file), so a file that starts like a ZIP is identified from its central directory: Office Open XML (by `[Content_Types].xml` and `word/`, `xl/`, `ppt/`), OpenDocument and EPUB (by the stored `mimetype` member), else ZIP. The type gives a category (program, script, document, archive, picture, video, audio, email, database, registry hive, shortcut, text, empty, other).
- **Renamed files:** an extension that promises a type the content contradicts is flagged (`ext_mismatch`) with what the name suggests (`expected_type`, e.g. "JPEG image" for a CSV named `holiday.jpg`). Extensions with no clear expectation, and contents libmagic can't type, are not flagged.
- **Encryption** (`encryption: {kind, detail}`): ZIP entries with the encryption flag (AES or ZipCrypto, from the local header), encrypted Office documents (an OLE container with `EncryptionInfo`/`EncryptedPackage`, the Word FIB encryption bit, an Excel `FILEPASS` record, PowerPoint `EncryptedSummary`; olefile), PDF encryption dictionaries (`/Encrypt` in the trailer area), and `HIGH_ENTROPY`: a file of at least 1 MiB, a whole number of 512-byte sectors, with no recognisable type and entropy of at least 7.95 bits per byte, as an encrypted container (VeraCrypt) is. Compressed media are high-entropy too but have a type, so they are not flagged.
- **Encrypted volumes** (`fs_index`, `app/forensic/volumes.py`): every volume is checked for LUKS (its `LUKS` magic) and BitLocker (libbde's volume signature check, which also recognises the BitLocker To Go discovery volume) before its file system is read. An encrypted volume is counted (`encrypted_volumes`) and reported as needing its recovery key or password; a To Go discovery volume's readable FAT part is still indexed.
- **Hash sets** (`app/forensic/hashsets.py`, `app/api/hashsets.py`): administrators (`HASHSET_MANAGE`) import a set as known good, known bad or notable, from an upload or (for large sets such as the NSRL) a file placed in `storage/hashsets/incoming`. Formats are recognised from the content: a plain list (one MD5, SHA-1 or SHA-256 per line; `md5sum`/`sha256sum` output; `#` comments), a CSV with `md5`/`sha1`/`sha256` columns, or the NIST NSRL RDS v3 SQLite (`FILE` table). A background `HASHSET_IMPORT` job writes each set to its own SQLite file (`storage/hashsets/<set id>.sqlite`) with one `WITHOUT ROWID` table of raw digests per algorithm, so even the NSRL is looked up in batches of 500 without loading it into memory or MongoDB; lines that are not a hash are counted, and an uploaded source is deleted once imported. Importing or deleting a set queues `hash_match` for every evidence item whose files were hashed.
- **Matching** (`hash_match`): a file in several sets takes the strongest kind (known bad, then notable, then known good) and lists every set it is in. Known-good files are hidden on the Files page by default; known-bad and notable files become `HASH_SET_MATCH` indicators (deleted files included), and a known-bad match notifies the case's investigator (on a re-match after a set changed, only when the number of known-bad files went up).
- **Finding the same content:** `GET /api/forensics/hash?case_id&digest` lists every file in the case with that MD5, SHA-1 or SHA-256, and the recovered, carved and extracted copies with that SHA-256. Keyword search accepts a hash.

### Content search and found data

- **Which text** (`app/forensic/textextract.py`), by the file's real type from `fileproc`: text files (text, scripts, email) are decoded (byte-order mark, UTF-8, UTF-16LE without a mark, else Windows-1252); PDFs with `pdftotext` (poppler, as an external tool with a timeout); Office Open XML (Word body, headers, footers, notes and comments; Excel shared and inline strings and values; PowerPoint slides and notes) and OpenDocument from their XML parts with defusedxml (DTDs and entities refused; parts over 32 MiB, or 96 MiB per document, are not expanded); RTF without control words, with escaped characters decoded; SQLite databases by reading their tables' text values, one per line, in a separate process (`app/forensic/sqlite_text.py`: read-only, immutable, `trusted_schema=OFF`, under `run_tool`'s timeout and memory limit), because their raw strings run one field into the next; everything else that may hold text (programs, registry hives, shortcuts, legacy Office, unknown data) as printable ASCII and UTF-16LE strings of at least 6 characters. Pictures, video, audio, archives, empty and encrypted files have no text here. A file is read at most 64 MiB deep and keeps at most 8 million characters; an evidence item keeps at most 1.5 billion.
- **Index** (`app/forensic/text_index.py`): one SQLite file per evidence with a `docs` table (path, inode, volume, deleted, method, encoding, byte-order mark, string spans) and an FTS5 table with the `trigram` tokenizer, so search is case-insensitive and matches parts of words (at least 3 characters). The index is built in a temporary file and renamed over the old one when complete, so searches keep working during a re-run; deleting the evidence deletes it.
- **Search** (`GET /api/forensics/content-search`): text mode finds the candidate files through the index and confirms every match in Python; regex mode uses RE2 (linear time; no backreferences), first narrowing the files by the longest literal of 3+ characters every match must contain (none when the pattern has an alternation or only optional or repeated parts), else scanning every file. A search stops after 15 seconds (or 20,000 candidate files) and says it is incomplete. Each file returns its match count and first 20 matches with 60 characters of context.
- **Byte offsets:** for decoded text the byte offset is the byte-order mark plus the length of the text before the match encoded in the file's encoding; for strings each run's byte offset and width (1 for ASCII, 2 for UTF-16LE) is stored; text taken out of PDF, Office, OpenDocument, RTF or SQLite files has no position in the file and says so. The viewer opens the hex view at an offset and highlights the match.
- **Found data** (`app/forensic/found_data.py`): email (domain with a 2-24 letter top-level label), URL (http, https, ftp with a host; trailing punctuation trimmed), IPv4 (each part 0-255; unspecified and reserved 240.0.0.0/4 such as netmasks left out; private or public), phone (international format with +, 8-15 digits), card (13-19 digits of a known brand's prefix and length, Luhn), IBAN (country length, mod-97), Bitcoin (Base58Check P2PKH/P2SH, Bech32/Bech32m `bc1`), Ethereum (0x + 40 hex; a mixed-case address must pass EIP-55, computed with an in-house Keccak-256), Aadhaar (4-4-4 digits, first 2-9, Verhoeff). One `entities` document per value per evidence item with its count, number of files and up to 100 occurrences (file, byte offset or text offset). Card and Aadhaar numbers are sensitive: lists, search and the report show them masked; `POST /api/forensics/entities/{id}/reveal` returns one in full and is audited (`SENSITIVE_VALUE_REVEALED`).
- **Every content search is audited** (`CONTENT_SEARCHED` with the query, mode and number of files).

### Archives, embedded files and unallocated space

- **Containers** (`app/forensic/containers.py`, by real type): ZIP (zipfile, read in place), the media and embedded objects of Office Open XML (`word|xl|ppt/media|embeddings/`) and OpenDocument (`Pictures/`, `Object */`) files, OLE compound files (embedded packages in `Ole10Native` streams, embedded documents in `Package` and `CONTENTS` streams; olefile), PDF attachments (`pdfdetach -list`, then `-save N -o <generated path>` one at a time), and everything 7-Zip reads (7z, RAR, tar, gzip, bzip2, xz, CAB...: `7z l -slt` first, then `7z x` into an empty folder). A container inside a container is opened too (two levels); a third level is listed on its container's record only.
- **Members** are `fs_entries` records whose path is the container's path, `!/`, and the member's name (`/Users/alice/Documents/export-backup.zip!/archive.7z!/q3-salaries.csv`), with `container` = {kind, parent, member, depth, encrypted, packed size, modified as recorded in the container (no time zone), store, note}. They inherit the top container's inode, volume and deleted flag, are hashed and typed with the same code as files (`process_blob`), and so are matched with hash sets, scanned with YARA, indexed for content search and scanned for found data. The Files list shows them in their own tab (`members=true`); the file-system counts leave them out; the overview counts them as `archive_members`.
- **Safety:** members are written under generated names (their own names are only data) in `storage/analysis/members/<EVID>/<run>/`; 7-Zip unpacks into an empty folder from which only regular files inside it are taken (links are never followed) under a file-size limit (`RLIMIT_FSIZE`); a member over 512 MiB, or one that expands more than 200 times (over 16 MiB), is listed but not extracted (possible archive bomb); one top-level container may unpack at most 4 GiB and an evidence item 32 GiB; containers over 8 GiB are not copied for 7-Zip or pdfdetach; encrypted members (and archives whose names are encrypted) are listed and flagged, never decrypted; 7-Zip gets a dummy password so it never waits for input. Members can be viewed (`/api/forensics/members/{id}/content|preview|raw`) and recovered (`POST /api/forensics/members/{id}/recover`: hashed, in the chain of custody).
- **Unallocated space** (`app/forensic/modules/unallocated.py`): for each file system, `blkls -l` lists its unallocated blocks (kept as runs of consecutive blocks), and `blkls` streams their content into DFIP as it runs (`stream_tool`: the raw data is never written to disk). ASCII and UTF-16LE strings of 6+ characters are found across chunk boundaries and mapped to their byte offset in the volume, piece by piece where a string crosses from one run of free blocks into another; they are stored in documents of about a million characters in `<EVID>.unalloc.sqlite` (at most a billion characters per evidence item). Content search and found data read this index with the files' one; a hit shows *Unallocated space (p2048)* and opens the volume's raw bytes (`GET /api/forensics/evidence/{id}/volume?volume_id&start&length`, each page audited) at its offset. The data of a deleted file whose clusters were not reused is found here even when its directory entry is gone.

### Evidence sources

`app/forensic/source.py` puts evidence content behind one interface: `TskImageSource` reads a disk image (or an E01's raw working copy) in-process with pytsk3, and `DirectorySource` reads a folder of loose files (later: unpacked triage packages). A volume is named by a `volume_id` (`p<start sector>`, `p0` for a bare file system; later `p<start>/vss<n>` and `pkg`); `fs_entries`, `FILE_MACB` events and the content, preview, raw and recover endpoints accept it next to the older `offset=`. The system tests check that pytsk3 reads every file (including deleted ones) byte for byte as `icat` does.

### Deleted file recovery

`GET /api/forensics/evidence/{id}/files?deleted=true` lists deleted entries from the index; `POST /api/forensics/evidence/{id}/recover?inode=&offset=` recovers one with `icat` (NTFS `64-128-2` addresses are accepted), hashes it, records it in the chain of custody and keeps the original filename. `GET /api/forensics/artifacts/{artifact_id}/download` returns the recovered copy with its SHA-256 in `X-DFIP-SHA256`. Signature carving of unallocated space (`/carve`) uses PhotoRec (all signatures except the noisy `dovecot` one) or Scalpel with `backend/rules/scalpel.conf`.

### File viewer

`GET /api/forensics/evidence/{id}/content|preview|raw?inode=&offset=` reads a file inside the image without writing a copy: `icat` is streamed and only the requested bytes are kept (hex pages of up to 64 KiB, up to 256 MiB into the file; recover the file to go further). The same three endpoints exist under `/api/forensics/artifacts/{artifact_id}/` for recovered, carved and extracted files. The type shown is decided from the first bytes (PNG, JPEG, GIF, WebP, BMP, PDF, text), never from the name; HTML and SVG are shown as text, and images and PDFs (up to 20 MB) are served with `nosniff`, `Content-Disposition: attachment` and a sandbox Content-Security-Policy. Each view is recorded in the audit log (`FILE_CONTENT_VIEWED`).

### Known limitations

- FAT times are converted with the computer's time zone from the SYSTEM hive (or the one the investigator sets); without either they are shown as recorded and flagged. FAT keeps only the date of the last access.
- Only allocated artifact files are parsed automatically; deleted browser databases or hives must be recovered and parsed manually (`/artifacts/{id}/browser-parse?kind=`).
- Chromium cookie values and saved passwords, and Firefox saved user names and passwords, are not decrypted (DPAPI, NSS); Firefox downloads before version 26 (`downloads.sqlite`) are not read.
- Deleted SQLite rows are recovered from browser history tables only; tables holding numbers alone (such as `visits`) are not searched (they match random bytes too easily), overflow pages are followed only for rows read through a cell pointer, and old WAL generations (frames whose salt no longer matches) are skipped. A row's start can be overwritten by later rows; what is left is reported only when every column still fits.
- Email: PST/OST items other than messages and contacts (appointments, tasks, notes) are counted as messages without a body; embedded Outlook items (a message attached to a message) are listed, not extracted; archives attached to emails are not opened; S/MIME and PGP encrypted messages are listed with their encrypted part as an attachment. Thunderbird's newer maildir storage and Outlook for Mac are not read.
- Pictures and videos: HEIC/HEIF and camera raw pictures get metadata from ExifTool but no thumbnail (Pillow has no decoder for them); video thumbnails need a format ffmpeg reads; ExifTool's maker notes are not shown. OCR reads English only and can misread characters; handwriting is rarely read. Faces and objects in pictures are not recognised, and pictures are not classified (by design).
- Chat and cloud: Skype for Business, Teams, WhatsApp, Telegram and Signal messages are not parsed (see above); OneDrive's older `<cid>.dat` layout and Google Drive's older `snapshot.db` are not read; the OneDrive file list says what the client knew, not whether a file was downloaded to the disk.
- The Celery hard time limit (`CELERY_TASK_TIME_LIMIT`, default 30 min) bounds analysis of very large images; raise it for multi-terabyte evidence.
- Multi-segment E01 sets (`.E02`...) are not supported by upload yet.
- An E01 needs free space for its raw working copy (the full media size) in `storage/analysis/working`. Partitions, file details and recovery for an E01 are available once its first analysis has prepared the copy.
- AFF/AFF4 uploads are accepted but have not been tested with this Sleuth Kit build.
- Jump Lists (`AutomaticDestinations-ms`) and shell-item (IDList) details of shortcuts are not parsed. Shortcut header times describe the target file, not when it was opened.
- Prefetch format version 31 (Windows 11 24H2) is read by libscca but has not been verified with DFIP; an unexpected version is reported as a warning.
- Registry: ShellBags of the Windows XP layout in NTUSER.DAT are read when present but have only been tested with UsrClass.dat; transaction logs are applied through regipy's recovery code and have not been tested here with a real dirty hive. Deleted registry keys (in hive free space) are not recovered.
- NTFS: `$LogFile` is not replayed or parsed; `$I30` index slack (names of deleted files left in directory indexes) is not read; only USN record versions 2 and 3 are read; the timestomping rules are heuristics that copying, archives and some installers can also trigger in user folders. The Sleuth Kit's `usnjls` stops at the first record that crosses a cluster boundary on small-cluster volumes, so the tests compare it only up to that point.
- Jump Lists, Timeline, thumbnails, SRUM, search index: only Windows Vista and later layouts are read; the SRUM database is read as it is (records Windows still held in its transaction logs are not replayed); Windows 11's `Windows.db` layout follows published research and has been tested only with a database written to it, not with a real one; the thumbnail-to-file link needs the search index to know the file. Times are stored to the millisecond (MongoDB's precision); FILETIMEs carry 100-nanosecond detail that is not kept.
- Event logs: only `.evtx` files at their usual place are read (not logs exported elsewhere, and not Windows XP `.evt`); event messages are not rendered from provider message files (the catalog describes the events an investigation needs, others show their data); recovered records whose template is gone cannot be read by libevtx and are counted as unreadable. The Sigma subset has no correlation rules, field-reference or CIDR modifiers, and no `near` aggregations.
- Encrypted volumes are recognised but not opened; unlocking BitLocker and LUKS with a key is a later addition. Encrypted files are flagged, never decrypted.
- Types come from the first 64 KiB of each file. File processing reads every file once; on very large disks the quick profile skips it.
- Content search covers files in the file index (allocated and deleted), archive members and the strings of unallocated space; slack space (the unused end of a file's last cluster) is not read. Content search reads SQLite tables' current values (deleted rows are recovered for browser history only). Text in pictures and scans is read by OCR (full profile).
- Values found in the strings of a binary file can run into the bytes next to them when nothing separates them.

`scripts/test-image/make-ntfs-image.sh` (in a privileged container: ntfs-3g mounts the volume through FUSE) builds `storage/test-images/dfip-ntfs-disk.dd`, alice's office desktop on NTFS (`make_ntfs.py`): SecureDelete.exe and archiver.zip with their Zone.Identifier streams, a note hidden in `notes.txt:hidden.txt`, `budget-2025.txt` with its `$SI` times set back to 2 March 2024 (the `$FILE_NAME` times kept, as Windows would), and `payroll-copy.csv` renamed to `AAAAAAAA.AAA`, overwritten and deleted. Files are written under faketime so creation times land in both `$SI` and `$FN`; ntfs-3g keeps no USN journal, so `$Extend/$UsnJrnl` (with `$J` and `$Max`) is created through libntfs-3g before the files and its 20 records written at the end. `dfip-ntfs-disk.manifest.json` holds the ground truth.

## High-volume operation

Jobs run in the `celery_worker` service (Redis broker). Scale with more workers or `--concurrency`; consider retry policy, dead-letter queues and resource isolation for production.

## Specialist validation

Tool versions, parser configurations, timezone assumptions, hash algorithms, acquisition methods and examiner actions should be recorded in case SOPs and reports. Do not treat a parser output as a conclusion without examiner review.

## Integrated specialist pipeline

DFIP now wires the forensic orchestrator to an allow-listed tool runner. The Docker image installs Sleuth Kit, libewf, ExifTool, tshark, YARA, `strings`, and `file` where available in the base distribution. The application detects tool availability at runtime and never invokes a shell command through `shell=True`.

### Examination sequence

1. Acquire evidence and calculate SHA-256.
2. Preserve the original object read-only.
3. Run `mmls` to identify partition boundaries.
4. Run `fsstat` and recursive `fls` for filesystem examination.
5. Use `istat` for inode metadata.
6. Use `icat` to recover a selected inode into the controlled analysis area.
7. Hash recovered output before further analysis.
8. Run ExifTool, strings, YARA, tshark, or Volatility against recovered/appropriate artifacts.
9. Persist tool output and provenance as forensic artifacts.
10. Record investigator actions in audit and chain-of-custody records.

The original forensic image is never passed to a tool with a write flag. Recovery outputs are stored separately under `storage/analysis/recovered`.
